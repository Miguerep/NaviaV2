# Development Context and Requirements for NaviaV2 (MVP)

## 1. Project Context

Navia is a mobile application (built with Flutter and a Python/FastAPI backend) that acts as an AI-powered smart tour guide. The objective of the MVP is to generate, adapt, and narrate personalized travel itineraries in real-time based on the user's location, interests, and preferred pace. The interface must be highly accessible ("WhatsApp-style") and designed for non-technical users.

## 2. Current Repository Status (Frontend & Backend)

- **Frontend (Flutter):**
  - Basic navigation is set up using `go_router` with a tabbed structure (`Explore`, `Itinerary`, `Guide`, `Profile`) and an initial Onboarding flow.
  - State is currently managed using `Provider` (`TripProvider`, `AppSettings`).
  - The Itinerary screen (`ItineraryScreen`) currently has hardcoded mock data and does not communicate with the AI to get the actual trip structure.
  - There is a `NaviaApi` class that already communicates with a backend to search for places (`searchPlaces`) and routes (`getRouteWalking`).
  - There is a basic `SpeechService` that currently reads static UI text via local TTS.
- **Backend (FastAPI):**
  - Basic structure is set up with empty routers for `chat`, `itinerary`, `places`, and `trips`.

## 3. Action Plan and Technical Requirements to Implement

You (the AI programming agent) must execute the following tasks in priority order to complete the core MVP features:

### Task 1: Complete Onboarding Flow (Preference Capture)

**MVP Requirement:** A 2 to 3 screen flow to capture trip duration, interests (art, gastronomy, history), and travel pace (relaxed, intensive).

- **Action:** Currently, only `DestinationScreen` and `TripDatesScreen` exist. Create new screens in the Onboarding flow to capture **interests** and **travel pace**.
- **Action:** Update `TripProvider` to store these new variables and ensure they are sent to the backend at the end of the Onboarding to generate the initial trip.

### Task 2: Real-Time Geolocation and Permissions

**MVP Requirement:** Request location permissions upon launch to pinpoint the user's city and retrieve relevant nearby Points of Interest (POIs).

- **Action:** Integrate geolocation and permissions into the Flutter app. You have the freedom to choose the best packages for this task (e.g., `geolocator` and `permission_handler`).
- **Action:** Request the necessary location permissions when the app starts (or at the beginning of the Onboarding).
- **Action:** Capture the current GPS coordinates and pass them to the services/API layer to feed the initial trip generation.

### Task 3: Automatic Language Detection (i18n)

**MVP Requirement:** Detect the device's system language to set the default locale for both the User Interface (UI) and the AI Agent's responses.

- **Action:** Set up an internationalization system in Flutter. **You MUST use Flutter's native `intl` package for this.**
- **Action:** Capture the device's locale (e.g., `es_ES`, `en_US`) during startup in `main.dart` or `NaviaApp`.
- **Action:** Add this language parameter (`locale`) to the headers or body of the requests in `NaviaApi` so the backend knows in which language to generate the itinerary text and audio.

### Task 4: API Contracts & Data Models Design (CRITICAL)

**Status:** There are currently NO predefined JSON structures or Pydantic models for the API endpoints.

- **Action (Backend & Frontend):** You are responsible for **designing the JSON contracts** from scratch.
- **Action:** Create the necessary Pydantic schemas in the FastAPI backend (e.g., for generating itineraries, sending chat messages, and returning audio files).
- **Action:** Create the corresponding Dart data classes in the Flutter frontend with proper `fromJson`/`toJson` methods to ensure seamless communication with the backend you just designed.

### Task 5: Dynamic Itinerary and Chatbot Connection

**MVP Requirement:** Users can request real-time changes via chat (e.g., "It's raining, change today's plan to indoor museums"), and the AI will update the database and the itinerary UI instantly using _Function Calling_.

- **Action (Frontend):** Remove the hardcoded data from `ItineraryScreen`. Connect this screen to `TripProvider` or create a new `ItineraryProvider` that consumes the itinerary endpoint via `NaviaApi`.
- **Action (Frontend):** Implement the logic for the `GuideScreen` to act as a chat interface. Chat requests must be sent to the backend chat endpoint you designed in Task 4.
- **Action (Frontend):** Automatically refresh the Itinerary if the chat endpoint returns a flag indicating that the route was modified.

### Task 6: Refine Audio Narration Engine (TTS)

**MVP Requirement:** An integrated audio player that reads a historical summary generated by the AI for a specific monument.

- **Action:** Modify the current `SpeechService`. Instead of using local TTS to read static text from the UI, it must call the backend endpoint to request an AI-generated summary or directly stream/play the URL of the generated audio file.

## 4. General Considerations and Rules for the Agent

- Maintain the existing architecture based on `Provider` for dependency injection and state management unless it is strictly necessary to scale to another solution.
- Follow the style guidelines defined in `NaviaTheme` to maintain the high contrast and large typography requested in the accessibility requirements.
- When implementing new API calls in `navia_api.dart`, correctly handle exceptions using the existing `ApiError` class.
- Provide code step-by-step, explaining the files being modified.
